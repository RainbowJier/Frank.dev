> 原文：[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)
> 作者：Prithvi Rajasekaran，Anthropic Labs 团队成员

过去几个月里，我一直在研究两个相互关联的问题：如何让 Claude 产出高质量的前端设计，以及如何让它在无需人工干预的情况下构建完整的应用程序。这项工作源于我们早期在前端设计技能和长时间运行编码智能体 Harness 方面的探索——我和同事们通过提示工程和 Harness 设计，将 Claude 的表现提升到了远超基线的水平——但两者最终都遇到了天花板。

为了突破瓶颈，我寻找了那些能在两个截然不同的领域中通用的全新 AI 工程方法——一个由主观审美定义，另一个由可验证的正确性和可用性定义。受生成对抗网络（GAN）的启发，我设计了一个包含**生成器**和**评估器**智能体的多智能体架构。要构建一个能可靠且具有审美判断力的评估器，首先需要开发一套将"这个设计好不好"这样的主观判断转化为具体、可评分标准的评估准则。

随后，我将这些技术应用于长时间自主编程，延续了早期 Harness 工作中的两个经验：将构建任务分解为可处理的单元，以及使用结构化产物在会话之间传递上下文。最终成果是一个三智能体架构——规划器、生成器和评估器——在多小时自主编程会话中产出了丰富的全栈应用程序。

## 为什么朴素实现会力不从心

我们之前已经展示了 Harness 设计对长时间运行的智能体编码具有显著影响。在早期实验中，我们使用一个初始化智能体将产品规格分解为任务列表，再由编码智能体逐个功能实现，最后通过结构化产物在会话间传递上下文。更广泛的开发者社区也汇聚了类似的洞见，例如"Ralph Wiggum"方法使用钩子或脚本来保持智能体在持续迭代循环中运行。

但一些问题仍然持续存在。对于更复杂的任务，智能体仍然倾向于随时间推移偏离轨道。在分解这个问题时，我们观察到执行此类任务的智能体存在两种常见失败模式。

首先是模型倾向于在长任务中随着上下文窗口填满而失去连贯性（参见我们关于上下文工程的文章）。一些模型还表现出"上下文焦虑"——当接近它们认为的上下文限制时，会过早地结束工作。上下文重置——完全清空上下文窗口并启动一个全新的智能体，结合结构化交接来传递前一个智能体的状态和后续步骤——可以同时解决这两个问题。

这与压缩（compaction）不同：压缩是将对话的早期部分在原地摘要，使同一智能体可以在缩短的历史记录上继续工作。虽然压缩保持了连续性，但它无法给智能体一个全新的起点，这意味着上下文焦虑可能仍然存在。重置提供了一个全新的起点，代价是交接产物需要包含足够的状态信息，以便下一个智能体能够干净地接手工作。在我们早期的测试中，我们发现 Claude Sonnet 4.5 表现出的上下文焦虑如此强烈，以至于仅靠压缩不足以实现强劲的长任务表现，因此上下文重置成为 Harness 设计的必要环节。这解决了核心问题，但增加了每次 Harness 运行的编排复杂性、token 开销和延迟。

第二个我们之前未涉及的问题是自我评估。当被要求评估自己产出的工作时，智能体倾向于自信地赞美——即使对于人类观察者来说，质量明显平庸。这个问题在主观任务（如设计）中尤为突出，因为没有等价于可验证软件测试的二元检查。一个布局是否感觉精致还是平庸是一个判断问题，而智能体在给自己的工作打分时总是偏向正面。

然而，即使在确实有可验证结果的任务中，智能体有时仍表现出会阻碍其完成任务的糟糕判断力。将执行工作的智能体与评判工作的智能体分离，被证明是解决此问题的有力手段。这种分离本身并不能立即消除那种宽容态度——评估器仍然是一个倾向于对 LLM 生成输出慷慨有加的 LLM。但将一个独立的评估器调校为持怀疑态度，远比让生成器对自己产出的作品持批评态度要可行得多，一旦存在了外部反馈，生成器就有了具体的迭代目标。

## 前端设计：让主观质量变得可评分

我从前端设计开始实验，因为自我评估问题在这里最为明显。没有任何干预的情况下，Claude 通常倾向于安全、可预测的布局——技术上功能齐全，但视觉上毫不出众。

两个洞见塑造了我为前端设计构建的 Harness。首先，虽然美学不能完全被简化为一个分数——而且个人品味始终会有差异——但可以通过编码设计原则和偏好的评分标准来提升美学质量。"这个设计美不美？"很难一致地回答，但"这个设计是否遵循了我们的良好设计原则？"给了 Claude 一个具体的评分依据。其次，通过将前端生成与前端评分分离，我们可以创建一个反馈循环，推动生成器产出更出色的结果。

基于此，我编写了四项评分标准，并在提示中同时提供给生成器和评估器智能体：

- **设计质量：** 设计是否感觉像一个连贯的整体，而不是零件的集合？在这方面表现优秀意味着颜色、排版、布局、图像和其他细节组合在一起，创造出独特的氛围和身份。
- **原创性：** 是否有自定义决策的证据，还是说这只是模板布局、库默认值和 AI 生成模式的堆砌？人类设计师应该能识别出有意的创意选择。未修改的现成组件——或 AI 生成的明显痕迹（如白色卡片上的紫色渐变）——在这一项上不合格。
- **工艺：** 技术执行水平：排版层级、间距一致性、色彩和谐度、对比度比率。这是一项能力检查而非创意检查。大多数合理的实现在默认情况下表现尚可；失败意味着基本功出了问题。
- **功能性：** 独立于美学的可用性。用户能否理解界面的功能，找到主要操作，并在不需要猜测的情况下完成任务？

我在工艺和功能性之上更强调设计质量和原创性。Claude 在工艺和功能性上默认已经表现良好，因为所需的技术能力通常对模型来说是自然的。但在设计和原创性上，Claude 经常产出最多只能说平庸的作品。这些标准明确惩罚了高度通用的"AI 垃圾"模式，通过更重地加权设计和原创性，推动模型在美学上承担更多风险。

我使用带有详细分数分解的少样本示例来校准评估器。这确保了评估器的判断与我的偏好保持一致，并减少了迭代间的分数漂移。

我在 Claude Agent SDK 上构建了这个循环，使编排保持简洁。生成器智能体首先根据用户提示创建 HTML/CSS/JS 前端。我给评估器提供了 Playwright MCP，使其能够在评分每个标准并撰写详细评语之前直接与实时页面交互。实际上，评估器会自行导航页面，截图并仔细研究实现，然后生成评估结果。反馈作为下一次迭代的输入流回生成器。每次生成运行 5 到 15 次迭代，每次迭代通常会推动生成器朝更加独特的方向发展，以响应评估器的评语。因为评估器是在主动导航页面而非对静态截图评分，每个周期需要实际的墙钟时间。完整运行长达四个小时。我还指示生成器在每次评估后做出战略决策：如果分数趋势良好则继续优化当前方向，如果方法不奏效则转向完全不同的美学风格。

在各次运行中，评估器的评估在迭代中改善后趋于平稳，但仍有提升空间。一些生成过程是增量式优化的，另一些则在迭代间经历了剧烈的美学转向。

标准的措辞以我没有完全预料到的方式引导了生成器。包含"最好的设计是博物馆级别"之类的短语将设计推向了特定的视觉收敛，这表明与标准相关的提示直接塑造了输出的特征。

虽然分数在迭代中总体上有所改善，但模式并不总是完全线性的。后期的实现通常整体上更好，但我经常发现我偏好某个中间迭代而非最后一个。实现复杂性也倾向于在各轮中增加，生成器在响应评估器反馈时会追求更宏大的方案。即使在第一次迭代时，输出也明显优于完全没有提示的基线，这表明标准和相关语言本身在评估器反馈引导进一步优化之前，就已经将模型从通用默认值中引导出来了。

在一个值得注意的例子中，我提示模型为一个荷兰艺术博物馆创建网站。到第九次迭代时，它为一家虚构的博物馆产出了一个干净的深色主题着陆页。页面视觉上精致，但基本符合我的预期。然后在第十次循环中，它完全放弃了这种方法，将网站重新构想为一种空间体验：一个用 CSS 透视渲染棋盘格地板的 3D 房间，以自由形式位置挂在墙上的艺术品，以及基于门口而非滚动或点击的画廊房间间导航。这是一种我以前从未在单次生成中见过的创意飞跃。

## 扩展到全栈编码

带着这些发现，我将这种受 GAN 启发的模式应用于全栈开发。生成器-评估器循环自然地映射到软件开发生命周期，其中代码审查和 QA 扮演着与设计评估器相同的结构性角色。

### 架构

在我们早期的长时间运行 Harness 中，我们通过一个初始化智能体、一个逐功能工作的编码智能体以及会话间的上下文重置，解决了连贯的多会话编码问题。上下文重置是一个关键突破：该 Harness 使用 Sonnet 4.5，它表现出了前面提到的"上下文焦虑"倾向。创建一个在上下文重置间都能良好工作的 Harness 是保持模型专注任务的关键。Opus 4.5 在很大程度上自行消除了这种行为，因此我能够从这个 Harness 中完全去掉上下文重置。智能体在整个构建过程中作为一次连续会话运行，由 Claude Agent SDK 的自动压缩机制处理上下文增长。

在这项工作中，我在原始 Harness 的基础上构建了一个三智能体系统，每个智能体解决我在之前运行中观察到的特定缺陷。该系统包含以下智能体角色：

**规划器：** 我们之前的长时间运行 Harness 要求用户预先提供详细的规格。我想自动化这一步，所以我创建了一个规划器智能体，它接收一个简单的 1-4 句提示，并将其扩展为完整的产品规格。我提示它在范围上要有雄心，并专注于产品背景和高层技术设计而非详细的技术实现。这种强调是因为担心如果规划器试图预先指定细粒度的技术细节且出错了，规格中的错误会级联到下游实现中。更明智的做法是约束智能体要产出的交付物，让他们在工作中自行摸索路径。我还要求规划器在产品规格中寻找融入 AI 功能的机会。（示例见文末附录。）

**生成器：** 早期 Harness 中的逐功能方法在范围管理方面效果良好。我在此应用了类似的模型，指示生成器以冲刺模式工作，每次从规格中选取一个功能。每次冲刺使用 React、Vite、FastAPI 和 SQLite（后期 PostgreSQL）技术栈实现应用，生成器被指示在每个冲刺结束时进行自我评估，然后交接给 QA。它还拥有 git 进行版本控制。

**评估器：** 早期 Harness 产出的应用程序虽然看起来令人印象深刻，但当实际使用时仍然存在真实的 bug。为了捕获这些问题，评估器使用 Playwright MCP 像用户一样点击浏览运行中的应用程序，测试 UI 功能、API 端点和数据库状态。然后它根据发现的 bug 以及一套以前端实验为蓝本的评分标准（此处改编为覆盖产品深度、功能性、视觉设计和代码质量）对每次冲刺进行评分。每个标准都有硬性阈值，任何一个低于阈值就会导致冲刺失败，生成器会收到关于出问题的详细反馈。

在每个冲刺之前，生成器和评估器会协商冲刺合约：在编写任何代码之前，就那块工作的"完成"标准达成一致。这之所以存在，是因为产品规格是有意保持高层次的，我需要一个步骤来弥合用户故事和可测试实现之间的差距。生成器提出它将构建什么以及如何验证成功，评估器审查该提案以确保生成器正在构建正确的东西。两者迭代直到达成一致。

通信通过文件处理：一个智能体写入文件，另一个智能体读取并回应——要么在同一文件中，要么通过一个新文件让前一个智能体依次读取。然后生成器根据商定的合约进行构建，再将工作交接给 QA。这保持了工作忠实于规格，而不会过早过度指定实现细节。

### 运行 Harness

对于这个 Harness 的第一个版本，我使用了 Claude Opus 4.5，将用户提示同时用于完整 Harness 和单智能体系统进行对比。我选择 Opus 4.5 是因为这是我开始实验时可用的最佳编码模型。

我使用以下提示来生成一个复古视频游戏制作器：

> _创建一个 2D 复古游戏制作器，功能包括关卡编辑器、精灵编辑器、实体行为系统和可玩的测试模式。_

下表显示了 Harness 类型、运行时长和总成本。

| **Harness** | **时长** | **成本** |
| --- | --- | --- |
| 单智能体 | 20 分钟 | $9 |
| 完整 Harness | 6 小时 | $200 |

Harness 的成本是单智能体的 20 倍以上，但输出质量的差异是显而易见的。

我期望的是一个界面，我可以在其中构建关卡及其组成部分（精灵、实体、瓦片布局），然后按下播放键来实际游玩关卡。我先打开了单智能体运行的输出，初始应用程序似乎符合预期。

但随着我点击浏览，问题开始浮现。布局浪费空间，固定高度的面板导致大部分视口空白。工作流程僵化。尝试填充关卡时提示我先创建精灵和实体，但界面中没有任何引导朝向这个顺序。更重要的是，实际的游戏是坏的。我的实体出现在屏幕上但没有任何东西响应输入。深入研究代码发现实体定义和游戏运行时之间的连接是断开的，表面上没有任何迹象表明问题出在哪里。

评估完单智能体运行后，我将注意力转向 Harness 运行。这次运行始于同一个单句提示，但规划器步骤将该提示扩展为分布在十个冲刺中的 16 个功能的规格。它远远超出了单智能体运行尝试的范围。除了核心编辑器和游玩模式外，规格还要求精灵动画系统、行为模板、音效和音乐、AI 辅助精灵生成器和关卡设计器，以及带可分享链接的游戏导出功能。我给规划器提供了我们的前端设计技能，它阅读并使用该技能为应用程序创建了一套视觉设计语言，作为规格的一部分。对于每个冲刺，生成器和评估器协商合约，定义冲刺的具体实现细节和用于验证完成的可测试行为。

该应用程序立即展现出比单智能体运行更多的精致和流畅。画布使用了整个视口，面板尺寸合理，界面具有一致的视觉身份，与规格中的设计方向保持一致。单智能体运行中出现的一些笨拙感仍然存在——工作流程仍然没有明确指示你应该在尝试填充关卡之前先构建精灵和实体，我不得不通过摸索来弄清这一点。这读起来更像是基础模型的产品直觉缺陷，而非 Harness 设计要解决的问题，尽管它确实指出了一个 Harness 内有针对性的迭代可以进一步提升输出质量的方向。

在使用编辑器时，新运行相较于单智能体运行的优势变得更加明显。精灵编辑器更丰富、功能更完善，工具面板更清晰、颜色选择器更好用、缩放控制更实用。

因为我要求规划器在规格中融入 AI 功能，该应用还内置了 Claude 集成，让我可以通过提示来生成游戏的不同部分。这显著加速了工作流程。

最大的差异在游玩模式中。我实际上能够移动我的实体并玩游戏。物理效果有一些粗糙之处——我的角色跳上平台后最终与平台重叠，直觉上感觉不对——但核心功能是有效的，而单智能体运行没有做到。移动了一会儿后，我确实遇到了 AI 关卡构建的一些限制。有一堵高墙我无法跳过，所以被卡住了。这表明有一些常识性改进和边缘情况，Harness 可以进一步处理以完善应用。

阅读日志可以清楚地看到，评估器使实现始终与规格保持一致。在每个冲刺中，它遍历冲刺合约的测试标准，通过 Playwright 操控运行中的应用程序，对任何偏离预期行为的情况提交 bug。合约非常细粒度——仅冲刺 3 就有 27 个覆盖关卡编辑器的标准——评估器的发现足够具体，可以直接采取行动而无需额外调查。下表展示了评估器识别的几个问题示例：

| **合约标准** | **评估器发现** |
| --- | --- |
| 矩形填充工具允许拖拽填充选定瓦片的矩形区域 | **失败** — 工具仅在拖拽起点/终点放置瓦片，而非填充区域。`fillRectangle` 函数存在但在 mouseUp 时未正确触发。 |
| 用户可以选择并删除已放置的实体生成点 | **失败** — `LevelEditor.tsx:892` 的删除键处理器要求同时设置 `selection` 和 `selectedEntityId`，但点击实体只设置了 `selectedEntityId`。条件应为 `selection \|\| (selectedEntityId && activeLayer === 'entity')`。 |
| 用户可以通过 API 重新排序动画帧 | **失败** — `PUT /frames/reorder` 路由定义在 `/{frame_id}` 路由之后。FastAPI 将 'reorder' 匹配为 frame_id 整数并返回 422："无法将字符串解析为整数"。 |

让评估器达到这个水平花了大量工作。开箱即用的话，Claude 是一个糟糕的 QA 智能体。在早期运行中，我观察到它识别出了合理的问题，然后说服自己这些不是什么大问题，还是批准了工作。它也倾向于浅层测试，而非探索边缘情况，所以更隐蔽的 bug 经常被遗漏。调校循环是阅读评估器的日志，找到其判断与我判断不同的示例，然后更新 QA 的提示来解决这些问题。经过多轮这样的开发循环，评估器的评分方式才达到了我认为合理的水平。即便如此，Harness 输出仍然展示了模型 QA 能力的局限：小布局问题、某些地方感觉不直观的交互，以及评估器未彻底测试的更深嵌套功能中未发现的 bug。显然还有更多验证空间可以通过进一步调校来捕获。但与单智能体运行相比——后者的应用核心功能完全不工作——提升是显而易见的。

### 迭代优化 Harness

第一组 Harness 结果令人鼓舞，但它也笨重、缓慢且昂贵。逻辑上的下一步是找到在不降低性能的前提下简化 Harness 的方法。这部分是常识，部分是一个更一般原则的体现：Harness 中的每个组件都编码了一个关于模型自身无法完成什么的假设，而这些假设值得进行压力测试——既因为它们可能不正确，也因为随着模型改进它们可能很快过时。我们的博客文章《构建有效智能体》将底层思想表述为"找到尽可能简单的解决方案，仅在需要时增加复杂性"，这是任何维护智能体 Harness 的人都会反复遇到的一个模式。

在第一次简化尝试中，我大幅削减了 Harness 并尝试了一些新的创意想法，但无法复现原始版本的性能。也很难分辨 Harness 设计中哪些部分实际上是承载重量的，以及以什么方式承载。基于那次经验，我转向了更系统的方法：一次移除一个组件，审查它对最终结果的影响。

在经历这些迭代循环的同时，我们也发布了 Opus 4.6，这为进一步减少 Harness 复杂性提供了动力。有充分的理由预期 4.6 将比 4.5 需要更少的脚手架。从我们的发布博客来看："[Opus 4.6] 规划更仔细，更长时间地维持智能体任务，能在更大的代码库中更可靠地操作，并且具有更好的代码审查和调试技能来捕获自己的错误。"它还在长上下文检索方面有了显著提升。这些都是 Harness 原本构建来补充的能力。

### 移除冲刺结构

我首先完全移除了冲刺结构。冲刺结构帮助将工作分解为模型可以连贯处理的单元。鉴于 Opus 4.6 的改进，有充分理由相信模型可以原生地处理这项工作而无需这种分解。

我保留了规划器和评估器，因为每个都继续提供明显的价值。没有规划器，生成器会范围不足：面对原始提示，它会直接开始构建而不先规划工作，最终创建出一个比规划器产出的功能更少的应用。

移除冲刺结构后，我将评估器改为在运行结束时进行单次通过而非按冲刺评分。由于模型能力更强了，它改变了评估器在特定运行中是否关键的权重，其有用性取决于任务相对于模型可以可靠独立完成的部分处于什么位置。在 4.5 上，这个边界很近：我们的构建处于生成器可以单独出色完成的能力边缘，评估器在整个构建中捕获了有意义的问题。在 4.6 上，模型的原始能力提高了，边界向外移动了。以前需要评估器检查才能连贯实现的任务现在通常在生成器独立处理的范围内，对于这些任务，评估器变成了不必要的开销。但对于构建中仍然处于生成器能力边缘的部分，评估器继续提供实质性的提升。

实际意义是，评估器不是一个固定的"是或否"决策。当任务超出当前模型可以可靠独立完成的范围时，它是值得成本的。

在结构简化的同时，我还增加了提示来改进 Harness 如何将 AI 功能融入每个应用——具体是让生成器构建一个能够通过工具驱动应用自身功能的真正智能体。这需要大量迭代，因为相关知识足够新，Claude 的训练数据对此覆盖稀薄。但经过足够的调校，生成器正确地构建了智能体。

### 更新后 Harness 的结果

为了测试更新后的 Harness，我使用以下提示生成一个数字音频工作站（DAW）——一个用于作曲、录音和混音歌曲的音乐制作程序：

> _使用 Web Audio API 在浏览器中构建一个功能完整的 DAW。_

运行仍然很长且昂贵，约 4 小时和 $124 的 token 成本。

大部分时间花在了构建器上，它连贯运行了两个多小时，不需要 Opus 4.5 所需的冲刺分解。

与之前的 Harness 一样，规划器将单行提示扩展为完整的规格。从日志中我可以看到，生成器模型在规划应用和智能体设计、连接智能体以及在交接给 QA 之前进行测试方面做得很好。

话虽如此，QA 智能体仍然捕获了真实的问题。在它的第一轮反馈中，它指出：

> 这是一个出色的应用程序，具有优秀的设计保真度、可靠的 AI 智能体和良好的后端。主要的失败点是功能完整性——虽然应用看起来令人印象深刻且 AI 集成运行良好，但几个核心 DAW 功能仅是展示性质的，缺乏交互深度：剪辑无法在时间线上拖动/移动，没有乐器 UI 面板（合成器旋钮、鼓垫），也没有可视化效果编辑器（EQ 曲线、压缩器仪表）。这些不是边缘情况——它们是使 DAW 可用的核心交互，而规格明确要求了它们。

在它的第二轮反馈中，它再次捕获了几个功能缺失：

> 剩余问题：
> - 音频录制仍然是占位代码（按钮切换但没有麦克风采集）
> - 通过边缘拖拽调整剪辑大小和剪辑分割未实现
> - 效果可视化是数字滑块而非图形化的（没有 EQ 曲线）

生成器在自行运作时仍然容易遗漏细节或将功能做成占位代码，而 QA 在捕获这些最后一英里问题上仍然有价值，供生成器修复。

根据提示，我期望一个可以创建旋律、和声和鼓型、将它们编排成歌曲、并在整个过程中获得集成智能体帮助的程序。

该应用程序远非专业的音乐制作程序，智能体的歌曲创作技能显然还有很大的改进空间。此外，Claude 实际上无法听到声音，这使得 QA 反馈循环在音乐品味方面的效果大打折扣。

但最终应用拥有了一个功能音乐制作程序的所有核心组件：在浏览器中运行的可用编排视图、混音器和传输控件。除此之外，我能够完全通过提示创建一个短歌曲片段：智能体设定了节奏和调性、铺设了旋律、构建了鼓轨道、调整了混音器电平并添加了混响。歌曲创作的核心原语都在，智能体可以自主驱动它们，使用工具端到端地创建一个简单的制作。你可以说它还没有完美到位——但它正在接近。

## 下一步

随着模型的持续改进，我们可以大致预期它们能够工作更长时间，处理更复杂的任务。在某些情况下，这意味着模型周围的脚手架随时间推移会变得不那么重要，开发者可以等待下一个模型并看到某些问题自行解决。另一方面，模型越强大，就有越多空间来开发能够实现超出模型基线能力的复杂任务的 Harness。

基于此，这项工作中有一些值得继续推进的经验。始终是一个好习惯来对正在构建的模型进行实验，阅读它在真实问题上的追踪日志，并调校其性能以达到你想要的结果。在处理更复杂的任务时，有时通过分解任务并将专业智能体应用于问题的各个方面来获得提升空间。而当新模型发布时，通常是一个好习惯来重新审视 Harness，剥离不再对性能起承载作用的部分，并添加新的部分以实现以前可能无法达到的更高能力。

从这项工作中，我的信念是，有趣的 Harness 组合空间不会随着模型的改进而缩小。相反，它在移动，而 AI 工程师有趣的工作是持续找到下一个新颖的组合。
