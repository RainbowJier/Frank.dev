## 一、什么是存储引擎？

如果把 MySQL 比作一个餐厅，**存储引擎**就是厨房的"炒菜方式"——同样一道菜（SQL），不同的存储引擎用不同的方式来"存"和"取"数据。

MySQL 的设计是"可插拔存储引擎"，SQL 解析、连接管理这些都是通用的，数据怎么存、怎么加锁、支不支持事务，由引擎决定。

```sql
-- 查看当前 MySQL 支持的所有引擎
SHOW ENGINES;

-- 查看默认引擎（MySQL 5.5 起默认是 InnoDB）
SHOW VARIABLES LIKE 'default_storage_engine';
```

## 二、InnoDB vs MyISAM：最重要的对比

在 MySQL 5.5 之前，MyISAM 是默认引擎，主打读速度快。但互联网业务发展之后，订单、支付、库存都需要事务，InnoDB 逐渐成为主流，5.5 起成为默认。

| 对比维度 | InnoDB | MyISAM |
| --- | --- | --- |
| **支持事务** | ✅ 支持 | ❌ 不支持 |
| **锁的粒度** | 行锁（并发更好）| 表级锁（写时整张表锁住）|
| **崩溃恢复** | 自动通过 Redo Log 恢复 | 需要手动修复，风险高 |
| **外键约束** | ✅ 支持 | ❌ 不支持 |
| **索引结构** | 聚簇索引（主键和数据在一起）| 非聚簇（数据另存）|
| **适用场景** | 订单、用户、任何需要事务的 | 历史归档只读、极少数特殊场景 |

**结论：新项目一律用 InnoDB，没有理由用 MyISAM。**

```sql
-- 查看数据库里每张表用的是什么引擎
SELECT TABLE_NAME, ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'mysql_zero_to_one';
```

## 三、InnoDB 为什么并发更好？

MyISAM 写数据时**锁整张表**，同一时间只有一个写操作能进行。想象一下，一个大教室，每次只允许一个人进去写黑板，其他人全部在门外等。

InnoDB 用**行级锁**，只锁住被修改的那一行。不同的人修改不同的行，可以同时进行，并发能力大幅提升。

## 四、其他引擎：什么场景用什么

### Memory 引擎：数据存在内存里

- **特点**：极快，但重启后数据消失
- **适用场景**：临时统计、小型缓存、会话数据
- **不适合**：持久化数据，不能替代 Redis

```sql
-- 临时统计表：只在当前会话有效，连接断了自动删除
CREATE TEMPORARY TABLE tmp_daily_stats (
  user_id       BIGINT UNSIGNED,
  order_count   INT
) ENGINE=Memory;

INSERT INTO tmp_daily_stats VALUES (1, 5), (2, 3);
SELECT * FROM tmp_daily_stats;
-- 连接断开后，这张表自动消失
```

### CSV 引擎：数据存成 CSV 文件

- **特点**：文件可以直接用 Excel 打开，便于交换
- **适用场景**：需要把数据导出给其他系统用
- **不适合**：正常业务表，因为没有索引

### Archive 引擎：压缩存储

- **特点**：数据高度压缩，只能插入和查询，不能更新
- **适用场景**：日志归档、审计记录
- **不适合**：需要频繁更新的数据

## 五、如何选择存储引擎？

```text
需要事务吗？
  ├─ 是 → InnoDB（99% 的场景）
  └─ 否 → 数据需要持久保存吗？
           ├─ 否 → Memory 临时表
           └─ 是 → 只写不改、要归档吗？
                    ├─ 是 → Archive
                    └─ 否 → 还是用 InnoDB，最保险
```

> 即使不需要事务，InnoDB 的行锁和崩溃恢复也比 MyISAM 可靠，所以通用选 InnoDB 准没错。

---

### 常见误区提醒

1. **整个库只能用一种引擎**：不对，每张表可以单独指定引擎。但要注意，跨引擎的操作无法在同一个事务里保证原子性。

2. **MyISAM 读更快，所以读多写少的场景用 MyISAM**：这个说法早就过时了。现代 InnoDB 的 Buffer Pool、MVCC 让普通读性能差距极小，而 InnoDB 还能做并发写和事务。

3. **Memory 引擎可以替代 Redis**：Memory 里的数据服务器一重启就没了，还占用 MySQL 连接，不适合做应用层缓存。

### 本章核心总结

- 存储引擎决定数据怎么存、怎么锁、支不支持事务
- InnoDB 支持事务+行锁+崩溃恢复，是现代业务的标准选择
- Memory 存内存、CSV 存文件、Archive 做归档，都是特殊场景
- **默认选 InnoDB，没有充分理由不换**
